# Documentation Development

[Development](README.md)

SnapshotFS uses a docs-as-code workflow. Guides and references live beside the
source code, are reviewed as Markdown, and build into a static searchable site.

## Stack

| Tool | Role |
| --- | --- |
| [Sphinx](https://www.sphinx-doc.org/) | Builds and validates the complete site. |
| [MyST-Parser](https://myst-parser.readthedocs.io/) | Lets Sphinx read CommonMark-style `.md` files. |
| [Furo](https://pradyunsg.me/furo/) | Provides the responsive HTML theme. |
| `sphinx.ext.autodoc` | Extracts the public Python API from signatures and docstrings. |
| `sphinx.ext.intersphinx` | Resolves links to Python's documentation. |
| `sphinx.ext.viewcode` | Links generated API entries to highlighted source. |
| `sphinx-autobuild` | Runs a live-reloading local preview server. |
| Read the Docs | Builds, searches, versions, and hosts the static site. |

Documentation dependencies are isolated in the `docs` dependency group in
`pyproject.toml` and locked in `uv.lock`. They are not runtime dependencies of
the `snapshotfs` package.

## Source And Output

Authored source is stored under `docs/`. `docs/index.md` is the site root and its
hidden MyST `toctree` defines navigation and ensures every published page is
included in the build.

```text
docs/
├── cli/          Task-oriented command-line guides
├── concepts/     Data-model and behavior explanations
├── development/ Maintainer and extension documentation
├── library/      Task-oriented Python guides
├── reference/    Generated and exact technical reference
├── conf.py       Sphinx configuration
└── index.md      Site root and navigation tree
```

Generated HTML is written to `docs/_build/` and ignored by Git. Do not commit
that directory. The Markdown source and generated `docs/reference/cli.md` are
committed so they remain useful directly on GitHub and in a checkout.

## Build Locally

Install all development and documentation dependencies:

```bash
uv sync --all-groups
```

Build the site with warnings treated as errors:

```bash
uv run sphinx-build -W --keep-going -b html docs docs/_build/html
```

Open `docs/_build/html/index.html`, or run a live-reloading server while writing:

```bash
uv run sphinx-autobuild docs docs/_build/html
```

Check external links separately:

```bash
uv run sphinx-build -b linkcheck docs docs/_build/linkcheck
```

The regular strict build validates MyST syntax, internal links, navigation, API
imports, and duplicate references. Link checking contacts external services, so
it is kept separate from the deterministic build.

## Python API Generation

`docs/reference/api.md` uses `sphinx.ext.autodoc` to render the public
`snapshotfs` package. The page wraps the reStructuredText autodoc directive in a
MyST `eval-rst` fence; narrative content around it remains ordinary Markdown.

The top-level `snapshotfs.__all__` list is the canonical public API and is also
checked by package-export tests. Prefer documenting that surface rather than
automatically exposing implementation modules. Public signatures and docstrings
therefore serve both code users and the generated reference.

Autodoc imports `snapshotfs` during a build. The top-level package intentionally
loads the FUSE adapter lazily, so API documentation does not require the optional
Linux FUSE dependencies. Keep optional or platform-specific imports out of the
top-level import path unless they degrade safely.

After changing an exported signature or docstring, rebuild the site and inspect
the corresponding entry in `docs/_build/html/reference/api.html`.

## CLI Reference Generation

`docs/reference/cli.md` is generated by
`scripts/generate_cli_reference.py`. The file is committed and must not be
edited by hand.

The script constructs a fresh Click command tree with
`build_cli(default_registry())`, invokes every built-in command's help with a
fixed terminal width, and writes fenced plain-text output. Import commands are
invoked with `--source file` and `--parser windows-dir` before `--help`. This is
necessary because selected components dynamically contribute `INPUT`,
`--encoding`, and `--date-format`; generic command-tree inspection would omit
them.

Regenerate after changing commands, options, help text, or built-in component
parameters:

```bash
uv run python scripts/generate_cli_reference.py
```

Verify that the committed reference is current without modifying it:

```bash
uv run python scripts/generate_cli_reference.py --check
```

When adding a built-in command, add its help invocation to `CASES` in the
generator. When adding another built-in source/parser combination, include the
combination needed to expose its contextual parameters.

## Add Or Update Pages

Use ordinary relative Markdown links with the `.md` suffix so links work both on
GitHub and in Sphinx. Keep site-only MyST directives localized to pages that need
them.

When adding a page:

1. Create it in the audience-appropriate directory.
2. Link it from a nearby Markdown index or guide.
3. Add it without the `.md` suffix to the `toctree` in `docs/index.md`.
4. Run the generated-reference check and strict HTML build.
5. Inspect the rendered navigation, code blocks, and any generated API content.

Write task-oriented examples in `cli/` and `library/`, explanations in
`concepts/`, exact schemas and signatures in `reference/`, and maintainer-only
material in `development/`. Keep the root `README.md` concise and link into the
full documentation instead of duplicating complete guides.

## Hosted Builds

`.readthedocs.yaml` selects Python 3.12, installs the locked `docs` dependency
group with uv, checks that the generated CLI reference is current, and points
Read the Docs at `docs/conf.py`. Read the Docs then runs the Sphinx build and can
publish the default branch, release tags, and pull-request previews.

Repository maintainers must import the GitHub repository into Read the Docs and
choose which versions are active. See [Publishing the documentation](../publishing.md)
for that one-time setup and the local release workflow.
